# Wilson Eval3ngine Backup and Recovery Runbook

## What this recovery path is

Wilson Eval3ngine now includes an operational PostgreSQL physical-backup and point-in-time-recovery path rather than a metadata-only recovery scaffold. The implementation is designed around a simple rule: **a restore is not successful merely because bytes were copied back into place.** A backup has to be encrypted, attributable to the correct database and WAL timeline, covered by a signed manifest, recoverable with the configured KMS, supported by continuous real WAL, and reconciled to a trusted expected state after PostgreSQL reaches the requested recovery point.

The source implementation therefore establishes substantially more than the earlier Phase-1 recovery design. It still does **not** establish that a particular production deployment meets its RPO, RTO, retention, key-custody, object-durability, or disaster-recovery requirements. Those remain runtime claims that must be measured and retained for the actual environment.

The configured recovery objectives remain targets:

- **RPO target:** 15 minutes;
- **RTO target:** 4 hours;
- **default retention target:** 30 days.

A successful restore exercise records its measured duration. That measurement can contribute to an RTO assessment; the constant `RTO_HOURS = 4` cannot.

## The recovery model in plain language

A full backup begins with the identity of the PostgreSQL cluster: database name, system identifier, timeline, WAL-segment size, current LSN, and current WAL filename. WE3 then runs `pg_basebackup` in tar mode and streams its stdout directly through AES-256-GCM encryption. The physical backup is therefore not first written as a normal plaintext backup file under the backup root. A one-time 256-bit data-encryption key is generated by the configured KMS, the backup stream is encrypted with that key, and only the KMS-wrapped form of the data key is retained with the backup metadata.

Each encrypted object has two independent content identities. The plaintext SHA-256 identifies the backup bytes that were encrypted, while the ciphertext SHA-256 identifies the exact stored encrypted object. The ciphertext digest is also used as the local storage version. The manifest binds those values to the KMS key identity, PostgreSQL system identifier, timeline, WAL position, and backup object location. The canonical manifest is signed with Ed25519, and verification requires both a valid signature and a signer fingerprint that the operator has placed in the recovery trust registry.

WAL archives use the same envelope-encryption and signing model, but they are created only from actual PostgreSQL WAL segment files. WE3 parses the 24-hex PostgreSQL WAL filename and ties the segment to the system identifier, timeline, and WAL-segment size of the selected full backup. Restore planning sorts these recorded segments by PostgreSQL WAL sequence and rejects a plan if coverage does not begin with the base backup's ending segment or if a gap appears in the required sequence. No placeholder `segment_0`, `segment_1`, or synthetic WAL names are generated.

The final recovery step is a real isolated PostgreSQL start. WE3 decrypts and authenticates the full backup, extracts it into an empty restore data directory, decrypts the required WAL files into an isolated archive, writes PostgreSQL recovery settings, starts the restored server on loopback with `pg_ctl`, waits until recovery has reached the requested timestamp or LSN and the server has promoted, then reconciles the restored state. The restored server is stopped after the exercise. A recovery result is successful only when that sequence completes and reconciliation passes.

## Installation and explicit configuration

Recovery has dependencies that ordinary deterministic evaluation does not need:

```bash
python -m pip install -e ".[dev,backup]"
```

The operational interface is the dedicated command:

```bash
we3-backup --help
```

The dedicated CLI exists because physical database recovery should not quietly inherit development defaults such as SQLite or a local test key. The older flat `we3 backup-*` commands are retained only as compatibility surface; new recovery automation and documentation should use `we3-backup`.

A real operation needs an explicit PostgreSQL URL and backup root:

```bash
export WE3_DATABASE_URL='postgresql://we3@127.0.0.1:5432/wilson_eval3ngine'
export WE3_BACKUP_ROOT='/srv/we3-backups'
```

Do not place a production database password in shell history. Supply database credentials through the deployment's approved process environment, `.pgpass`/service mechanism, or secret-management integration appropriate to the environment. WE3 does not put the database password into the `pg_basebackup` command line; if the URL contains a password it is passed to PostgreSQL tooling through the child-process environment.

### KMS configuration

AWS KMS is the production-oriented KMS adapter included with the repository:

```bash
export WE3_BACKUP_KMS_PROVIDER='aws'
export AWS_REGION='us-east-1'
```

The KMS key is supplied to each create/archive command as a key ID, alias, or ARN understood by AWS KMS. The manifest records bounded, non-secret KMS identity such as the requested key ID, resolved key ID, ARN, key manager, origin, and multi-region flag. It never stores the plaintext data-encryption key.

The repository's `LocalKMSClient` remains useful for hermetic tests and disposable development exercises. It is deliberately opt-in for the backup CLI:

```bash
export WE3_BACKUP_KMS_PROVIDER='local'
export WE3_ALLOW_LOCAL_BACKUP_KMS='1'
```

That setting is **not** a production key-custody model. It exists so recovery logic can be tested without pretending that a local development key is an external managed KMS.

### Signing trust

Backup and recovery-baseline manifests use Ed25519 signing. Verification is not satisfied by a mathematically valid signature alone: the public-key fingerprint must also be trusted for the exercise.

The dedicated CLI reads trusted fingerprints from:

```bash
export WE3_BACKUP_TRUSTED_SIGNER_FINGERPRINTS='sha256-fingerprint-1,sha256-fingerprint-2'
```

A real deployment should populate that value from its approved recovery/signing governance rather than copying arbitrary fingerprints from an untrusted backup directory.

## 1. Create a full encrypted physical backup

```bash
we3-backup create \
  --key-id 'alias/we3-backup-production' \
  --signing-key '/secure/recovery-signing.pem'
```

The command first checks that the database URL is PostgreSQL and captures cluster identity. The native streaming implementation currently rejects clusters with user-defined tablespaces because a single stdout tar stream cannot safely describe external tablespace layout. For such deployments, use a target-specific managed backup adapter/service until native tablespace support is implemented rather than silently producing an incomplete backup.

`pg_basebackup` is executed with tar output and WAL fetch required for a consistent physical base backup. Its stdout is encrypted as it is read. Progress/error output is retained in the backup directory as `pg_basebackup.log`, while the encrypted backup object, canonical manifest, signature, and durable catalogue record are written only after the process succeeds.

A successful catalogue record includes the PostgreSQL system identifier, timeline ID, WAL-segment size, starting and ending LSN, ending WAL segment, plaintext and ciphertext SHA-256 values, resolved storage location/version, KMS key identity, signer fingerprint, backup duration, and tool version. Supplying a key ID without producing encrypted bytes is no longer considered an encrypted backup.

## 2. Archive real WAL segments

WE3 expects an external PostgreSQL archival mechanism to produce completed WAL files. Point the recovery CLI at those real archive files:

```bash
we3-backup wal-archive \
  --wal-file '/srv/postgres-wal/0000000100000000000000A4' \
  --base-backup-id 'backup_example' \
  --key-id 'alias/we3-backup-production' \
  --signing-key '/secure/recovery-signing.pem'
```

The WAL filename must be a valid 24-hex PostgreSQL segment name, its size must match the cluster's configured WAL-segment size, and its timeline must match the base backup. Re-archiving the same segment with the same plaintext digest is idempotent. Presenting different bytes for a segment name already in the catalogue is rejected because that condition indicates corruption, the wrong database/timeline, or an unsafe archive collision.

The application does not manufacture WAL data and does not replace PostgreSQL's `archive_command`/archive service. Its role is to ingest completed archive files into the same encrypted, signed, identity-bound evidence model as full backups.

## 3. Capture the state that recovery is expected to reproduce

A restore cannot be meaningfully reconciled if the only question is “did PostgreSQL start?” Before the protected recovery point is declared, capture a signed baseline:

```bash
we3-backup capture-baseline \
  --output '/secure/we3-recovery-baseline.json' \
  --signing-key '/secure/recovery-signing.pem'
```

The baseline records the expected counts for runs, classifications, metric snapshots, gate decisions, provenance edges, pending outbox events, and the terminal audit-chain hash for each project. Before signing, WE3 recomputes the audit chain using the same canonical event-hash function used by the normal audit ledger. A baseline is refused if that chain is already invalid.

This baseline is intentionally a separate trust object. A restore plan records its SHA-256 and will not execute against a different baseline. In a production governance process the baseline should be retained independently of the backup payload, because keeping both the evidence and the only copy of its expected state in one failure domain weakens recovery assurance.

## 4. Build a PITR plan and prove WAL continuity

For a timestamp target:

```bash
we3-backup plan \
  --timestamp '2026-08-22T04:00:00Z' \
  --baseline '/secure/we3-recovery-baseline.json'
```

For an exact LSN target, which is preferable when the recovery point is known precisely:

```bash
we3-backup plan \
  --timestamp '2026-08-22T04:00:00Z' \
  --target-lsn '0/4A12B6F0' \
  --baseline '/secure/we3-recovery-baseline.json'
```

The planner chooses the latest eligible full backup before the target, verifies its manifest/signature/trust/ciphertext/KMS decryptability, selects WAL only from the same PostgreSQL system identifier and timeline, and proves sequential coverage from the base backup's ending segment through the target. Every selected WAL object is verified before it becomes part of the plan.

Missing coverage is a hard stop. An absent base segment, a timeline mismatch, a gap in WAL sequence, a corrupted object, an untrusted signer, an invalid manifest, or insufficient coverage through the target produces an error instead of a “best effort” plan.

## 5. Execute the isolated restore

```bash
we3-backup restore \
  --timestamp '2026-08-22T04:00:00Z' \
  --target-lsn '0/4A12B6F0' \
  --baseline '/secure/we3-recovery-baseline.json' \
  --isolated-database-url 'postgresql://postgres@127.0.0.1:55433/postgres' \
  --data-directory '/srv/we3-restore/pgdata' \
  --signing-key '/secure/recovery-signing.pem'
```

The isolated database URL is restricted to loopback. The data directory must be empty. The extractor rejects path traversal, device entries, hard links, and symbolic links in the physical backup tar. That is why native backup currently rejects user-defined tablespaces instead of trying to recreate external link topology during restore.

WE3 decrypts every selected object only after ciphertext identity, canonical manifest hash, signer trust, signature validity, KMS unwrap, AES-GCM authentication tag, plaintext size, and plaintext digest are all verified. It then writes `restore_command`, the target timestamp or LSN, `recovery_target_action = 'promote'`, and `recovery.signal`, starts PostgreSQL on the isolated loopback port, and waits for `pg_is_in_recovery()` to become false.

If PostgreSQL fails to start, cannot reach the target, cannot find required WAL, or reconciliation fails, the operation raises an error and does not report success. The restored server is stopped in a `finally` path so a failed exercise is not left running as an accidentally trusted service.

## 6. Understand reconciliation

Reconciliation now follows the actual persistence schema instead of inferring unrelated state from audit payloads. In particular:

- pending delivery work is counted from `outbox_events` where status is not `delivered`;
- provenance population is counted from the real `provenance_edges` table;
- audit events are read with their complete hash inputs and the hash chain is recomputed project by project;
- run, classification, metric-snapshot, gate-decision, and provenance counts are compared with the signed baseline;
- terminal project audit roots must exactly match the signed baseline;
- discrepancies are retained explicitly instead of being reduced to one Boolean.

A reconciliation report can itself be signed. A passing result means the restored state matched the supplied trusted baseline under these checks. It does not mean every external artifact store, network control, identity provider, or provider endpoint outside the database has automatically been recovered; those deployment-specific dependencies need their own recovery evidence.

## 7. Read the retained restore evidence

Each executed restore writes `restore_execution.json` beneath the backup root's `restore-evidence/<plan-id>/` directory. The evidence includes:

- plan ID;
- measured start/completion time and duration;
- restore data and WAL-archive directories;
- PostgreSQL and `pg_ctl` versions;
- a SHA-256 of the PostgreSQL restore log;
- the full reconciliation result;
- the configured RPO/RTO targets accompanied by an explicit note that they are targets, not measurements.

CI uses an authorized disposable PostgreSQL cluster and preserves its runtime directory as a workflow artifact. This gives pull requests repeatable evidence that the implementation can actually perform backup, archive, replay, and reconciliation. It is still test-environment evidence, not proof about a production cluster.

## Verification and failure interpretation

`we3-backup verify <backup-id>` is intentionally stronger than checking whether a file exists. Verification fails when any of these conditions is true:

- catalogue record is missing or says the object is not encrypted;
- manifest, signature, or encrypted payload is missing;
- canonical manifest SHA-256 differs from the catalogue;
- signer fingerprint is not trusted;
- Ed25519 signature is invalid;
- manifest identity disagrees with catalogue identity;
- ciphertext size or SHA-256 differs;
- KMS cannot unwrap the recorded data key;
- AES-GCM authentication fails;
- decrypted plaintext size or SHA-256 differs.

This distinction matters operationally. A KMS access failure is not the same condition as storage corruption, and a valid ciphertext hash is not the same thing as a trusted manifest signature. Keep those failure classes separate during incident response so remediation targets the actual broken layer.

## Runtime prerequisites and boundaries

The native recovery implementation requires PostgreSQL client/server utilities discoverable through `PATH` or `pg_config`, and the Python `backup` extra installs `psycopg` plus `boto3`. AWS credentials/role resolution are delegated to the normal AWS SDK chain. Production operators should prefer workload identity/role-based access over long-lived KMS credentials.

The durable catalogue is `backup_catalog.v2.json` under the configured backup root. Writes are atomic and the catalogue survives process restart, so independent `we3-backup list`, verify, plan, and restore invocations operate over retained metadata rather than an in-memory mapping. The current native storage backend is filesystem-based and identifies each encrypted object's storage version by its ciphertext SHA-256. A production deployment still needs to place that backup root on storage whose durability, access policy, retention, legal hold, replication, and deletion controls satisfy the program. A local file path is not automatically immutable object storage.

Migration `008_backup_evidence_v2` augments the earlier recovery schema so a managed control plane can mirror the same system/timeline/WAL/integrity/storage identities. Migration `006_backup_and_recovery` remains untouched as migration history and should not be read alone as the current recovery contract.

## CI recovery exercise

The ordinary unit suite verifies encryption, KMS identity handling, PostgreSQL URL restrictions, WAL sequence arithmetic, signed baselines, durable catalogue reload, manifest/ciphertext tampering, and planning failures without requiring a running database.

The integration test is different. `tests/integration/test_backup_restore.py` is marked `runtime` and skips unless:

```bash
WE3_RUN_POSTGRES_RECOVERY_TEST=1
```

When enabled in the dedicated CI job it initializes a disposable PostgreSQL cluster, creates real database state, takes the encrypted physical backup, mutates the database, records the target LSN and signed baseline, forces/archives real WAL, exercises missing-WAL and tamper failures, restores to a second loopback cluster, and requires post-recovery reconciliation to pass. The CI job installs the `backup` dependencies and PostgreSQL tools explicitly and uploads the runtime directory as evidence.

## Return-to-service approval

The repository helper `create_recovery_verification_manifest()` requires two **distinct** approvers before it stops marking re-certification as required. Duplicate names are not counted twice. That helper records approval evidence but does not authenticate a human merely because a string was supplied; the deployment's identity and approval workflow remains responsible for proving who approved the recovery.

A restored production environment should not regain release authority until:

1. the selected backup and every required WAL object verify;
2. PostgreSQL reaches the intended target;
3. reconciliation passes against the approved signed baseline;
4. external storage/object evidence has been reconciled where applicable;
5. deployment-specific security/identity/network checks pass;
6. independent recovery approvals are recorded;
7. required release/certification checks have been rerun.

## Evidence worth retaining for every real exercise

| Evidence | Meaning |
|---|---|
| PostgreSQL system identifier and timeline | Identifies the database history being recovered. |
| Base-backup ID and ending LSN/WAL segment | Establishes the physical starting point. |
| KMS key identity + wrapped DEK metadata | Shows which managed key protected the object without exposing the DEK. |
| Plaintext and ciphertext SHA-256 | Binds encrypted storage to the exact protected backup bytes. |
| Canonical manifest + Ed25519 signature | Makes metadata/object identity tamper-evident and attributable to a trusted signer. |
| Actual WAL filenames and continuity | Shows that PITR used recorded PostgreSQL segments rather than synthetic names. |
| Signed recovery baseline | Defines the state the restored database is expected to reproduce. |
| PostgreSQL restore log + hash | Shows that recovery was actually executed and provides failure diagnostics. |
| Reconciliation report and discrepancies | Shows whether restored database evidence matches the expected state. |
| Measured duration | Supplies an observed input to RTO assessment. |
| Environment/storage/network identity | Connects software evidence to the deployment where the exercise occurred. |
| Independent approvals | Establishes accountable return-to-service authority. |

## Security rules

Never publish production database passwords, KMS credentials, private signing keys, private provider/network topology, raw production recovery logs, or other secret assurance data merely to demonstrate that the feature works. Public documentation should describe the contract and bounded result; sensitive runtime evidence belongs in the approved private evidence system.

Never weaken a failing recovery check to make a demonstration pass. Missing WAL, an untrusted signer, a changed ciphertext byte, an invalid audit link, pending outbox state, or a population discrepancy is exactly the kind of condition the recovery system exists to surface. Investigate and correct the cause instead of rewriting the evidence.

## What can be claimed after this implementation

It is accurate to say that the repository **implements** encrypted PostgreSQL physical backup, signed manifest verification, durable local backup cataloguing, real WAL-segment ingestion and continuity checks, isolated PITR execution, signed recovery baselines, schema-aware reconciliation, and a real disposable PostgreSQL CI exercise.

It is not accurate to say that an arbitrary deployment therefore “has a 15-minute RPO,” “has a 4-hour RTO,” “uses production KMS correctly,” or “has passed disaster recovery.” Those statements require evidence from the exact deployment, storage system, key authority, network boundary, database size/workload, and operational team being approved.
